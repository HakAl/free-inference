# Security Policy and Threat Model

`free-inference` is an open-source inference workbench and launch harness for coding agents on Apple Silicon macOS. It is built around a strict 5-rung data-control ladder (`local`, `enclave_weights_attested`, `enclave_runtime_attested`, `zdr_contract`, `standard_api`) with fail-closed admission checks and no silent cross-rung fallback.

## Threat Model and Trust Boundaries

Attested session windows default to 2 hours for interactive launches and permit at most 24 hours per fresh Touch ID authorization. `scripts/session status|start|stop|renew|watch` is an operator interface, outside agent sandboxes. Status uses an owner-only Unix socket (0700 directory, 0600 socket, peer-UID and server-PID checks) and returns a strict whitelist of counters, time, and non-secret session identity. Legacy or unverifiable sessions report UNKNOWN. A monotonic clock including sleep enforces expiry on admission, with a cleanup timer; stop and expiry cancel active streams.

Renewal requires a live, unexhausted session and fresh Secure Enclave authorization. It rotates the proxy token in an atomically published, mode-0600 generation-bound envelope before committing the new in-memory window. Failure after file publication fails closed. Request and spend caps do not reset. Trusted parent relays follow rotation without exposing the new token to OpenCode. A single retry after an auth race requires a nonce-bound HMAC proof of rejection before forwarding, the same server/session identity, and an advancing generation. Ambiguous failures are not retried. Worker deadlines and budgets remain independent. The protected control socket and token store remain inaccessible through the actual agent sandbox; no renewal tool is registered with MCP or OpenCode.

### What `free-inference` protects against

1. **Silent cross-rung downgrade or cloud fallback**:
   - `local_assist/client.py`, `scripts/opencode-local`, and `scripts/opencode-attested` enforce explicit data-control admission gates before any model request is sent.
   - `private-local` (Rung 1) admits only `local` models served on loopback (`127.0.0.1`, `localhost`, `[::1]`) with `HF_HUB_OFFLINE=1` and `TRANSFORMERS_OFFLINE=1` verified via the active server PID record (`pid_lstart`) and OS listener command line (`lsof` + `ps`).
   - `private-attested` (Rung 2/3) admits only localhost-bound attesting enclave proxies backed by `apiKeyKeychainService` (`se-key-proxy` + `tinfoil-proxy`), while keeping the `local_assist` MCP sub-calls pinned to Rung 1 (`http://127.0.0.1:8080/v1`) without exporting `LOCAL_ASSIST_ALLOW_ATTESTED_TEE` into the MCP child environment.
   - Rung 4 (`zdr_contract`) and Rung 5 (`standard_api`) are blocked from private coding workflows.

2. **Raw API key exposure to coding agents, config files, and child processes**:
   - Provider API keys for Rung 2/3/4/5 endpoints are never stored in `models.yaml`, shell profiles, or `.env` files, and are never passed to coding agents.
   - `scripts/se-key store <service>` (or `scripts/se-key migrate <service>`) seals the raw provider API key with a hardware-bound Secure Enclave P-256 private key (`CryptoKit.SecureEnclave.P256.KeyAgreement`, `.biometryCurrentSet`, `.privateKeyUsage`) using ephemeral P-256 ECDH key agreement + `HKDF<SHA256>` (info `"free-inference/se-ecies-v1/" + service`) + `AES.GCM.seal` (`se-ecies-v1`), storing only the verified outer ciphertext envelope (`<stem>.json`, mode `0600`) and lifecycle tombstone (`<stem>.state.json`, mode `0600`) in `~/.config/free-inference/se-envelopes/` (mode `0700`) with `service` bound as AES-GCM Additional Authenticated Data (AAD), write-time read-back authenticated decryption, and `envelope_sha256` integrity binding. Keeping the outer `SealedEnvelope` JSON in a dedicated `0700`/`0600` store instead of `login.keychain-db` eliminates legacy Keychain `CDHash` password prompts across binary rebuilds while keeping the private key hardware-bound in the Secure Enclave.
   - At runtime, `scripts/serve-model` generates an ephemeral `se-session-<64-hex>` bearer token (`0600` in `runs/.se-session-<id>.token`) and passes it to `bin/se-key-proxy` via an inherited pipe descriptor (`--session-token-fd <fd>`). `bin/se-key-proxy` calls `ptrace(PT_DENY_ATTACH, 0, 0, 0)`, prompts for Touch ID once to unseal the provider API key in memory, and validates the session token on `http://127.0.0.1:<port>/v1` before injecting the real upstream `Authorization: Bearer` header.
   - `se-key-proxy` verifies that its loopback upstream socket (`127.0.0.1:<port+1000>`) belongs to the expected `tinfoil-proxy` child PID and matching kernel process start time (`proc_pidinfo(PROC_PIDTBSDINFO)`) via `proc_pidfdinfo(..., PROC_PIDFDSOCKETINFO)` before forwarding the unsealed Bearer key.

3. **Unbounded session spend or prompt exfiltration via OpenCode defaults**:
   - Both `scripts/opencode-local` and `scripts/opencode-attested` generate an isolated `opencode.json` in `.home/opencode-private-*` with `autoupdate: false`, `share: "disabled"`, `snapshot: false`, `lsp: false`, `formatter: false`, `OPENCODE_DISABLE_PROJECT_CONFIG=1`, `OPENCODE_DISABLE_MODELS_FETCH=1`, and `webfetch`/`websearch`/`codesearch` set to `"deny"`.
   - `se-key-proxy` enforces per-session caps on chat requests (`--max-chat-requests`), output tokens (`--max-tokens-cap`, clamping `n` and `best_of` to `1` so worst-case output spend is bounded to a single completion per request), request body size (`--max-request-bytes`), stream duration (`--stream-timeout-seconds`), and session TTL (`--ttl-seconds`), and `scripts/opencode-attested` supports a pre-flight worst-case spend ceiling (`--max-session-usd`).

4. **Default interactive Seatbelt isolation, per-invocation credential custody, and outbound leak backstops (`local_assist/launch.py`, `local_assist/relay.py`, `config/plugins/credential-guard/server.js`, `tools/se_key_proxy/main.swift`)**:
   - **Zero `LOCAL_ASSIST_SESSION_TOKEN` or `OPENCODE_PASSWORD` in OpenCode or child environments**: `scripts/opencode-attested` and `scripts/opencode-local` scrub `LOCAL_ASSIST_SESSION_TOKEN`, `OPENCODE_PASSWORD`, and `OPENCODE_SERVER_PASSWORD` from their own `KERN_PROCARGS2` via anonymous pipe-FD handoff (`os.execve` + `_FREE_INFERENCE_TOKEN_FD`, closed immediately before spawning threads or children) and never export session tokens or daemon passwords into OpenCode.
   - **Parent-process `SessionAuthRelay` (`local_assist/relay.py`)**: `scripts/opencode-attested` runs an in-process loopback HTTP relay outside the OpenCode process tree that holds `se-session-*` in parent memory only, issues a per-invocation `oc-relay-<hex>` bearer token (`0400` in `<inv_dir>/opencode.json`), enforces constant-time auth (`hmac.compare_digest`) and `ttl_seconds` session expiry (`HTTP 401`, `code: "session_expired"`), and rejects outbound `/v1/chat/completions` payloads containing raw, `%XX`-encoded, `\uXXXX` JSON Unicode-escaped (via recursive parsed JSON string key/value inspection), standard/URL-safe base64, or Basic-auth variants of `se-session-*`, `oc-relay-*`, `worker-relay-*`, or the per-invocation `service.json` password with `HTTP 400` (`code: "credential_leak_blocked"`). `bin/se-key-proxy` enforces the same outbound credential-leak check as a final host-side backstop before upstream forwarding or `chatRequestsUsed` accounting.
   - **Per-invocation OpenCode service custody (`<isolated_home>/.invocations/<inv_id>/`)**: Every interactive CLI or TUI launch creates a `0700` per-invocation directory with a dedicated `0400` `.config/opencode/service.json` (`{"hostname": "127.0.0.1", "port": <ephemeral_port>, "password": "<random>"}`) and private `XDG_CONFIG_HOME` / `XDG_STATE_HOME` / `TMPDIR` while sharing `XDG_DATA_HOME` (`opencode.db`) for conversation persistence (`--continue`). On exit, the launcher reaps the per-invocation `opencode serve --service` daemon and removes `<inv_dir>`. Uncontained legacy homes containing `service.json` under `.local/state/opencode`, `.local/share/opencode`, or `.config/opencode` fail closed at startup until remediated via `./scripts/check-credential-containment --apply --operator-approved`.
   - **Interactive Seatbelt profile (`interactive.sb`) and `credential-guard` plugin**: Interactive `opencode` runs under `/usr/bin/sandbox-exec` (`compile_interactive_seatbelt_profile`), which confines `<inv_dir>` and `<isolated_home>` reads/writes plus `service_port` and `relay_port` loopback connections exclusively to `(process-path "<opencode_real>")`, blocks `/bin/ps` and `opencode` re-exec from child tools, blocks direct child connections to `:8081`/`:8082`/`:9081`/`:9082`/`:49374`, protects host secret stores (`~/.ssh`, `~/.aws`, `~/.config/free-inference`, `~/Library/Keychains`, `runs/`) while preserving `SSH_AUTH_SOCK` agent signing (`--allow-ssh-remote` for outbound TCP `22`), and runs a dedicated Mach-O `local-assist-python` + `local-assist-node` runtime so JavaScript eval assertions work without nested `sandbox-exec`. Inside OpenCode, `config/plugins/credential-guard/server.js` enforces Turn-1 MCP readiness (`session.hook("prompt")`), blocks restricted secret-store tool inputs (`tool.hook("execute.before")`), scrubs accidental credential patterns from tool outputs and `shell/*.out` spool files before SQLite/planner persistence (`tool.hook("execute.after")`), and blocks outbound HTTP body leaks (`session.hook("http.request")`).

5. **Unattended worker sandboxing (`--unattended-worker` / `--security-profile <path>`, `local_assist/security_profile.py`)**:
   - Supervisors such as `AgentComms` can launch unattended OpenCode workers on `scripts/opencode-local` or `scripts/opencode-attested` under an enforceable OS-level (`/usr/bin/sandbox-exec` Apple Seatbelt) and runtime-level (`opencode.json`) security profile.
   - **Two-tier kernel isolation (`opencode` vs child `shell` commands) and dedicated immutable `local_assist` runtime**: `worker.sb` uses `(process-path "<opencode_real>")` combined with `(deny process-exec (literal "<opencode_real>") (literal "<opencode_bin>"))` (allowing `process-exec` of `opencode` only from `/usr/bin/sandbox-exec` and `opencode` itself for its per-worker `opencode serve --service` daemon) so child shell commands cannot impersonate `opencode` or reach loopback inference/MCP ports (`8080`, `8081`, `9081`, `49374`, or `opencode`'s per-worker `service.json` port). When `mcp.enable_local_assist: true`, the launcher provisions dedicated read-only Mach-O copies `<isolated_home>/bin/local-assist-python` and `<isolated_home>/bin/local-assist-node` (`0500`) plus a self-contained read-only runtime snapshot `<isolated_home>/runtime` (`0400`/`0500`, bound via `<isolated_home>/lib/pythonX.Y/site-packages/local_assist_runtime.pth` and executed with `-I -m local_assist.server` and `PYTHONSAFEPATH=1`) so only `opencode` can execute `local-assist-python`, only `local-assist-python` receives `localhost:8080` network access, and `local-assist-python` never imports worker-writable code.
   - **Authenticated parent-process token relay (`_WorkerTokenRelay` / `SessionAuthRelay`)**: In `scripts/opencode-attested` worker mode, the launcher starts an in-process loopback HTTP relay outside the sandbox with a per-run `worker-relay-<hex>` bearer token checked in constant time (`hmac.compare_digest`), clamping `max_tokens`/`max_completion_tokens` (and clamping `n` and `best_of` to `1`), enforcing per-worker `max_chat_requests`, `max_request_bytes`, and outbound credential-leak rejection (`HTTP 400`), and requiring a finite positive `max_session_usd` ceiling (rejecting `NaN`/`inf`). The `se-session-*` token never enters `opencode.json` or the worker sandbox, and `localhost:8081` is kernel-denied inside `worker.sb`.
   - **Bounded filesystem reads/writes and default-deny `.git` and runtime protection**: `worker.sb` restricts reads under `/Users`, `/Volumes`, and `/private/tmp` to configured `read_roots`, `write_roots`, and `<isolated_home>`, denies reads and writes to host credential paths (`~/.agent-comms`, `~/.config/free-inference`, `~/.ssh`, `~/.aws`, `~/Library/Keychains`, `runs/`, `.home/`), denies writes to `free-inference` runtime code/scripts/config/venv/Python installation paths (`_collect_runtime_write_deny_paths`) even when nested inside a containing `write_root`, restricts writes to `<isolated_home>/.tmp` (plus `.local/`, `.cache/`) and configured `write_roots`, denies all writes to `.git` by default while allowing only working-tree git plumbing (`index`, `HEAD`, `ORIG_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `BISECT_*`, `MERGE_*`, `COMMIT_EDITMSG`, `packed-refs`, `gc.pid`, `info/refs`, `objects/`, `refs/`, `logs/`, `sequencer/`), and unconditionally blocks writes to `<isolated_home>/opencode.json`, `<isolated_home>/worker.sb`, `<isolated_home>/bin`, `<isolated_home>/lib`, `<isolated_home>/runtime`, `<isolated_home>/.config`, `<isolated_home>/.worker-owner.json`, `<isolated_home>/.unconfirmed-process-group.json`, `<isolated_home>/verified-models.json`, `<isolated_home>/pyvenv.cfg`, `.git/(hooks|config|config.worktree|info|modules|commondir|gitdir|worktrees|shallow|rebase-merge|rebase-apply)`, `.opencode`, `.env`, `.env.(local|development|production|staging|test|secret|secrets|private)`, `.envrc`, `.mcp.json`, `.gitmodules`, and caller-specified `protected_paths` (plus their ancestor directories to prevent parent-directory rename bypasses). Because `.git/rebase-merge` and `.git/rebase-apply` are write-denied to prevent `git-rebase-todo` `exec` command planting, interactive or stateful `git rebase` inside worker sandboxes is intentionally disabled (use `git merge`, `git cherry-pick`, or `git revert` instead).
   - **Mach / IPC lockdown, neutral git identity, and descriptor-pinned lifecycle/reaping**: `worker.sb` enforces `(deny job-creation)`, `(deny user-preference-read)`, `(deny user-preference-write)`, `(deny signal)` with `(allow signal (target same-sandbox))`, and `(deny mach-lookup)` with a minimal 6-service read-only logging/directory-info allowlist (omitting `com.apple.trustd*`, `com.apple.cfprefsd*`, `WindowServer`, `SecurityServer`, `launchservicesd`, and `pasteboard`). Worker runs set neutral `GIT_AUTHOR_*` / `GIT_COMMITTER_*` (`worker <worker@local>`) defaults and `LOCAL_ASSIST_WORKER_ID`, execute inside a dedicated process group (`run_worker_sandbox_lifecycle`) with confirmed `_terminate_process_group` escalation (`.unconfirmed-process-group.json`), multi-pass start-time-revalidated reaping (`ps eww` + fail-closed `lsof -d cwd`), nonblocking `O_NONBLOCK` + `S_ISREG` + size-capped log harvesting, and descriptor-pinned `openat`/`unlinkat`/`fchmod` tree removal (`_safe_rmtree_nofollow`). Note that a background child process that leaves the process group (`setsid`), `chdir`s outside `<isolated_home>`, and clears its own process environment (`env -i`) before the parent exits can evade user-space `ps eww` / `lsof -d cwd` matching while remaining confined by `worker.sb`.

### Residual Boundaries and Operational Disclosures

- **Per-invocation relay token in `<inv_dir>/opencode.json` (`oc-relay-*` / `worker-relay-*`)**:
  - OpenCode reads a per-invocation `oc-relay-*` (or `worker-relay-*`) token from its `0400` `<inv_dir>/opencode.json` file (`(process-path "<opencode_real>")` only) to authenticate to the parent-process `SessionAuthRelay`. Child `bash` tools are kernel-denied read access to `<inv_dir>` and loopback access to `relay_port`, `service_port`, and `:8081`. The `se-session-*` proxy token stays in the unsandboxed parent launcher process and `runs/.se-session-<id>.token` (`0600`) and can be revoked immediately with `./scripts/stop-model <model-id>`.
- **Operator-approved `bash` commands and `SSH_AUTH_SOCK`**:
  - Interactive `bash`, `edit`, `write`, and `patch` tools prompt for operator approval (`"ask"` unless `--allow-bash` or `--allow-edit` is explicitly passed). Approved `bash` commands run inside `interactive.sb`, which enforces `(deny network-outbound)` and `(deny network-bind)` by default (`--allow-shell-localhost-port <port>` opens explicit unreserved localhost dev ports; `--allow-ssh-remote` adds `mDNSResponder` lookup and outbound TCP `22`; outbound HTTPS `443` is not granted inside `interactive.sb`) while blocking host credential directories, `runs/`, `<inv_dir>`, and loopback control/inference ports.
  - `SSH_AUTH_SOCK` is passed through in `SAFE_ENV_ALLOWLIST` so approved `git` operations can use the host SSH agent while `~/.ssh` private keys remain read-denied.
- **Rung 1 offline verification boundary**:
  - `scripts/serve-model` sets `HF_HUB_OFFLINE=1` and `TRANSFORMERS_OFFLINE=1` by default for Rung 1 servers, and `scripts/verify-served-model --require-offline` verifies `hf_offline: true` in the `pid_lstart`-bound PID record and checks the live OS listener `--model` flag (`lsof` + `ps`) before `opencode-local` or `local_assist` sends a chat request. This is a pre-flight process and listener verification gate, not a kernel-level packet filter.
- **Trusted repository configuration (`models.yaml` `serve_command`)**:
  - `models.yaml` is operator-authored configuration inside the trusted repository root. For `runtime: proxy` models on Rungs 2/3, `serve_command` is split with `shlex.split` (`shell=False`) and checked by a heuristic localhost flag validator (`validate_custom_command_localhost`), which is a denylist that a shell or interpreter wrapper (`sh -c`, `python3 -c`) can bypass. Furthermore, `bin/tinfoil-proxy`'s pinned SHA-256 and Apple Developer ID signature are verified during `./scripts/setup`, not re-hashed at `serve-model` launch (while `bin/se-key-proxy` is checked via `verify_root_owned_binary_and_ancestors`). Operators should treat edits to `models.yaml` with the same review rigor as executable code.
- **Same-UID local compromise**:
  - Processes running as the same macOS user account share the same OS privilege domain. While `PT_DENY_ATTACH` blocks unprivileged debugger attachment to `se-key-proxy` and the raw API key never enters agent environments or disk files, `free-inference` does not claim protection against a compromised local user account or kernel-level attacker.
- **Runtime attestation vs. weight attestation**:
  - Rung 3 (`enclave_runtime_attested`) verifies the enclave TLS certificate, binary measurement, and Sigstore transparency log via `tinfoil-proxy`, and records the provider's declared `dm-verity` root hash in `provider_manifest_weights_hash`. Promotion to Rung 2 (`enclave_weights_attested`) requires independently reproducing the `dm-verity` root hash from audited Hugging Face weights via `modelwrap --verify`.

## Reporting a Vulnerability

Please report security vulnerabilities privately via GitHub Security Advisories (`Security -> Advisories -> Report a vulnerability` on the repository) rather than opening a public issue. Include:

- Affected component (`local_assist`, `se-key-proxy`, `scripts/serve-model`, `scripts/opencode-*`, or `models.yaml`)
- Minimal reproduction steps on macOS arm64
- Impact on the 5-rung data-control boundary or credential isolation
